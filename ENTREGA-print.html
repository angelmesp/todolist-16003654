4. Tipo de implementación

¿Qué tipo de implementación realizaron: local, remota, manual o automatizada?

Se hizo de las dos formas. Primero local, para comprobar el CRUD y la interfaz. Después remota y manual: SSH al servidor, build de la imagen y docker run. No se usó un pipeline de CI/CD; los pasos se ejecutaron a mano, que es lo que describe la estrategia Recreate de la guía.

¿Qué diferencias encontraron entre ejecutar localmente y desplegar en un servidor?

En local el proceso es un node directo en el puerto 8080. En el servidor hay que publicar un puerto libre, nombrar el contenedor y dejar la versión anterior disponible. El código es el mismo; cambia el empaquetado, la red y quién administra el proceso.

¿Qué riesgos existen al actualizar directamente una aplicación en producción?

Recreate detiene el contenedor actual antes de subir el nuevo, así que hay un momento sin servicio. Si la v2 falla y no se conservó la imagen 1.0, no hay a qué regresar. También se pierden datos en memoria, porque esta API no usa base de datos.

¿Qué ventajas proporciona Docker para mover software entre ambientes?

La imagen lleva runtime y dependencias. Local y servidor ejecutan el mismo artefacto. Versionar 1.0 y 2.0 permite actualizar y hacer rollback sin reinstalar Node a mano.

6. Actualización y rollback (Recreate)

La estrategia usada fue Recreate: se detiene y elimina el contenedor actual y se levanta la imagen nueva en el mismo nombre y puerto. 

docker stop todolist-16003654
docker rm todolist-16003654
docker run -d --name todolist-16003654 -p 3654:8080 \
  -e PORT=8080 -e APP_VERSION=2.0 angelmesp/16003654:2.0
# health: {"status":"ok","version":"2.0"}

Para simular un problema en v2 se regresó a la imagen 1.0, que se había dejado en el servidor: 

docker stop todolist-16003654
docker rm todolist-16003654
docker run -d --name todolist-16003654 -p 3654:8080 \
  -e PORT=8080 -e APP_VERSION=1.0 angelmesp/16003654:1.0
# health: {"status":"ok","version":"1.0"}

Después del rollback se volvió a dejar la 2.0 en ejecución, ya comprobado que la 1.0 sigue disponible.

7. Preguntas de análisis

¿Qué es una implementación de software?

Es el proceso de poner una aplicación construida en un ambiente donde los usuarios o el servicio la pueden usar: instalarla, configurarla, publicarla y comprobar que responde.

¿Qué diferencia existe entre desarrollo e implementación?

El desarrollo produce el código y las pruebas. La implementación lleva ese producto a un ambiente real (local empaquetado o servidor), con puertos, imágenes y operación del contenedor.

¿Qué problema resuelve Docker durante una implementación?

Evita el “en mi máquina sí corre”. La imagen incluye lo necesario para ejecutar la app, así que local y servidor usan el mismo paquete.

¿Por qué debemos versionar una imagen Docker?

Para saber qué se desplegó y para poder volver atrás. Si solo se usa latest, un rollback no tiene un punto fijo. Aquí 1.0 y 2.0 se conservaron a propósito.

¿Qué diferencia existe entre integración continua y entrega continua?

Integración continua (CI) automatiza build y pruebas al integrar cambios. Entrega continua (CD) deja el artefacto listo para producirse de forma repetible; el paso a producción puede seguir siendo una decisión humana.

¿Qué diferencia existe entre entrega continua y despliegue continuo?

En entrega continua el paquete queda preparado. En despliegue continuo cada cambio que pasa las pruebas se publica solo en producción, sin un visto bueno manual en cada release.

¿Qué es rollback y por qué es importante?

Es volver a una versión anterior cuando la nueva falla. En este ejercicio se demostró al detener la 2.0 y levantar de nuevo la 1.0. Importa porque reduce el tiempo de una falla en producción.

¿Qué ventajas presenta Blue/Green?

Se mantienen dos ambientes. El tráfico se cambia al nuevo cuando está listo. El anterior queda en espera, así el rollback es rápido y hay menos tiempo caído que con Recreate.

¿Qué ventajas presenta Canary?

La versión nueva se expone primero a una parte de los usuarios. Si las métricas se ven mal, se detiene el avance. Reduce el impacto de un error frente a actualizar a todos de una vez.

¿Por qué no es recomendable modificar manualmente producción?

Los cambios a mano no quedan en la imagen ni en Git. El siguiente contenedor los pierde, y otro ambiente no los replica. Lo correcto es cambiar el código, construir otra etiqueta y desplegar esa imagen.

¿Qué información debe verificarse después de un despliegue?

docker ps (estado y puertos), docker logs, /health y la interfaz en el navegador. En este caso se comprobó healthy, el log “TodoList vX.0 en puerto 8080” y el JSON de /health.
